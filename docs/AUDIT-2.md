### 'Recover' sweeps a customer's deposit into the operator's central wallet, writes no ledger row at all, and never credits the merchant — while the panel promises 'they settle to you like any other balance'
`backend/src/routes/account.ts:730` — business-logic — CONFIRMED

**Evidence.** Re-read the handler end to end (account.ts:685-749): claimForSweep -> adapter.sweepDeposit (:714) -> markSwept -> writeAudit -> 200 {success,txHash}. No other write of any kind.
Verified the missing ledger row directly rather than taking the claim on trust: `grep -n blockchain_transactions` across the tree shows the ONLY `direction='sweep'` INSERT in the codebase is workers/index.ts:377, inside processSweep — a path this route does not go through. I read both adapters' sweepDeposit to the end: evmAdapter.ts inserts only `'gas_funding'` (:535) and then returns `{txHash, amount, asset}` at :571 with no further write; tronAdapter.ts inserts only `'gas_funding'` (:299); bitcoinAdapter inserts nothing.
Confirmed the money therefore lands nowhere in the books: getBalanceWith/getAllBalances read only payments and payouts (payoutService.ts:893, 903) — no reference to unexpected_deposits — and getCommissionBalance's `collected` term reads `blockchain_transactions WHERE direction='sweep' AND status='confirmed'` (adminCommissionService.ts:107), which no recover row satisfies. So the funds are physically in the hot wallet, absent from the merchant's balance AND absent from the operator's accrued commission. Grepped every reference to unexpected_deposits across backend and both panels: the only consumers are the reaper's NOT EXISTS, the link-use predicate (paymentLinkService.ts:193, 527) and reconcileSweptExcess's row-resolver (workers/index.ts:198). No credit path exists.
The false promise is verbatim in the panel — client-panel/src/pages/UnexpectedDeposits.tsx:208: "Recovering moves the funds into the gateway's collection wallet, where they settle to you like any other balance. The money is safe until you do". This is the routine path, not an edge case: reapLateDeposits (workers/index.ts:703) files a row for every payment funded after expiry.

**Fix.** Split the handler on `row.asset === row.expected_asset`, which the table already records. LATE SAME-ASSET (the common case): after markSwept, do exactly what reconcileSweptExcess already does for a late arrival — write the sweep ledger row (`INSERT INTO blockchain_transactions (payment_id, direction, tx_hash, from_address, to_address, amount, token, asset, network, status, log_index) VALUES (…, 'sweep', …, -2) ON CONFLICT (tx_hash, log_index) DO NOTHING`, copied from workers/index.ts:377), then `UPDATE payments SET amount_received = amount_received + $amt, status='swept' WHERE id = $paymentId` so the existing settle tick creates the payout and takes commission normally. WRONG ASSET: hold it as a per-(network, asset) merchant credit the existing payout endpoint can draw on, and convert only on explicit opt-in at a quoted rate (clients.auto_convert_unexpected and max_slippage_bps already exist). Ship the ledger-row insert even if the credit lands later — without it the operator cannot reconcile the hot wallet at all. Until a credit path exists, change the copy at UnexpectedDeposits.tsx:208 to say the funds move to the gateway wallet and require support to settle; the current sentence is the specific thing that makes this a trust failure rather than a gap.

### A `failed` merchant/admin payout stays claimable after its reservation is released, so a BullMQ retry re-broadcasts it alongside the replacement — uq_payouts_active_payment does not cover payment_id IS NULL
`backend/src/services/payoutService.ts:489` — business-logic — CONFIRMED

**Evidence.** REPRODUCED LIVE (scratchpad/dbl.mjs and dbl2.mjs, both inside BEGIN…ROLLBACK), and the control proves the asymmetry.
CASE payment_id NULL: inserted M1 gross 100 status `failed`; inserted M2 `pending` for the same client — it succeeded, so uq_payouts_active_payment did not fire. Then ran executePayout's EXACT claiming UPDATE (payoutService.ts:483-494, verbatim including the commission fold) against M1: returned {status:'processing', net_amount:'100.000000000000000000'} — i.e. it proceeds to sign and broadcast a second 100 USDT.
CONTROL, payment_id set: same sequence with a swept payment attached — the re-claim of P1 died with `23505 duplicate key value violates unique constraint "uq_payouts_active_payment"`. So auto payouts are protected and merchant/admin ones are not.
Confirmed the index predicate against the live DB via pg_indexes: `ON payouts (payment_id) WHERE payment_id IS NOT NULL AND status <> 'failed'`. Confirmed both creation paths pass no paymentId: routes/payouts.ts:164 (merchant) and the admin panel's create modal, so payment_id IS NULL for exactly the rows the index skips.
Confirmed the release: `failed` is the only status omitted from every reservation sum (payoutService.ts:891, 903 and getAllBalances), so the balance snaps back and requestPayout's advisory-lock guard legitimately passes the replacement. **Fix.** Two lines and one index. (2) Add the missing half of migration 016: `CREATE UNIQUE INDEX CONCURRENTLY uq_payouts_active_manual ON payouts (client_id, network, asset) WHERE payment_id IS NULL AND status IN ('pending','processing','sent','unresolved');` so two live merchant withdrawals for the same (client, network, asset) cannot coexist at all. (3) Send an Idempotency-Key from client-panel/src/lib/api.ts createPayout — the middleware already honours it and this closes the double-click window in front of both.

**Evidence.** Reproduced live and it WORSENED during verification. Two fresh readings: chain_cursor.BEP20 = 124,476,442 (frozen, identical across both reads ~9 min apart) while eth_blockNumber on the configured RPC (https://data-seed-prebsc-1-s1.binance.org:8545) returned 0x76b62bc=124,478,140 (auditor), then 0x76b6900=124,479,744 (me) — behind grew 1,698 -> 2,206 -> 3,302 blocks. `queryFilter failed` count in listener.log grew 126 (auditor) -> 191 -> 299 during this session; scanRange histogram is 185+ at the floor value 10 vs one occurrence each of 2000/1000/500/250/125/62/31/15, i.e. it halved eight times to the floor in the first minute and every failure since has been a no-op halve. Read evmListener.ts:970-985 myself: the ONLY recovery is the halve at line 980 plus `return` without advancing the cursor; there is no sleep, no failover endpoint, no escalation. Do NOT put lag in GET /health — index.ts:80-92 deliberately keeps it dependency-free and rate-limit-exempt; add a separate GET /health/ready (currently 404s) that reports per-network max(head - last_scanned_block) and fails above a threshold, and point the readiness probe at that.
